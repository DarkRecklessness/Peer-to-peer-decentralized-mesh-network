# Тестирование корректности построения сети

В корневой директории проекта запустите 

```
MESH_NODES=10 MESH_CONNECT_TIMEOUT=600 cargo test --release test_n_nodes_resilient_mesh -- --nocapture
```

Можно изменять параметры **MESH_NODES** и **MESH_CONNECT_TIMEOUT** по своему усмотрению. 

Где **MESH_NODES** - кол-во узлов для теста, что объединяются в одну сеть. **MESH_CONNECT_TIMEOUT** - время ожидания соединения всех узлов, в секундах. 

_Не рекомендуется ставить **MESH_NODES** >25 (это может привести к долгим таймаутам со стороны публичной инфраструктуры relay серверов и pkarr)._ 

_Не рекомендуется ставить **MESH_CONNECT_TIMEOUT** <180 (узлы могут не успеть соединиться)._

# Нагрузочное тестирование P2P-сети (Docker Environment)

Здесь описан процесс развертывания и тестирования P2P VPN сети с использованием Docker.
### Утилиты
Для нагрузочного тестирования используются утилиты iperf3 (см. [документацию](https://iperf.fr/iperf-doc.php)), tc (см. [документацию](https://man7.org/linux/man-pages/man8/tc.8.html)) и netem (см. [документацию](https://man7.org/linux/man-pages/man8/tc-netem.8.html))

---

## Пошаговая инструкция по тестированию

### Шаг 0: Подготовка

Перед тестированием необходимо скомпилировать программу из корневой директории проекта

```
cargo build --release
```

Дальше переходите в директорию для тестов

```
cd tests/docker-tests
```

### Шаг 1: Запуск тестового кластера

Откройте терминал и запустите контейнеры. Эта команда соберет образы и запустит оба узла сети.

```
sudo docker compose up
```

_(Рекомендуется оставить это окно открытым, чтобы видеть логи работы ваших VPN-узлов)._

### Шаг 2: Подключение к терминалам узлов

Откройте **два новых окна терминала** (по одному для каждого узла) и подключитесь к ним с помощью `docker exec`:

**Терминал 1 (Узел 1 — Сервер):**

```
sudo docker exec -it vpn_node1 /bin/bash
```

**Терминал 2 (Узел 2 — Клиент):**

```
sudo docker exec -it vpn_node2 /bin/bash
```

### Шаг 3: Настройка сервера (Узел 1)

В терминале `vpn_node1` запустите серверную часть утилиты для тестирования скорости:

```
iperf3 -s
```

Сервер перейдет в режим ожидания входящих подключений.

### Шаг 4: Установка прямого соединения (Узел 2)

Прямое P2P-соединение внутри одной локальной docker-сети может занять некоторое время. Чтобы убедиться, что туннель успешно поднят, в терминале `vpn_node2` запустите пинг виртуального IP-адреса первого узла:

```
ping 10.67.1.1
```

Ожидайте. Как только пинг стабилизируется в районе **0–3 мс**, это означает, что прямой P2P-туннель успешно установлен, и узлы общаются напрямую. Нажмите `Ctrl+C`, чтобы остановить пинг.

## Проведение тестов производительности

Находясь в терминале `vpn_node2`, вы можете измерить скорость одним из следующих способов:

### Вариант А: Тестирование скорости через VPN-туннель (Зашифрованный трафик)

Измеряет реальную пропускную способность P2P-туннеля.

```
iperf3 -c 10.67.1.1 -t 15
```

### Вариант Б: Тестирование через локальную сеть Docker (В обход VPN)

Полезно для оценки накладных расходов. Если вы хотите посмотреть максимальную пропускную способность между контейнерами без шифрования, используйте их локальные Docker-адреса:

```
iperf3 -c 172.20.0.10 -t 15
```

## Эмуляция плохой сети

Чтобы проверить устойчивость туннеля к реальным условиям интернета, примените один из сценариев к сетевому интерфейсу на `vpn_node2`.

_Выполняйте эти команды во втором (клиентском) терминале или прерывайте серверный, применяйте правила и снова запускайте `iperf3 -s`._

**Сброс сети до идеального состояния (Перед каждым новым тестом, или используйте аргумент change вместо add):**

```
tc qdisc del dev eth0 root
```

### 5 сценариев для тестирования:

**1. Среднее качество сети (Приближено к LTE интернету)**

Задержка 50 мс, небольшой джиттер и потеря 0.1% пакетов.

```
tc qdisc add dev eth0 root netem delay 50ms 10ms loss 0.1%
```

**2. Высокий пинг**

Стабильно высокий пинг (300 мс) без сильных потерь.

```
tc qdisc add dev eth0 root netem delay 300ms 15ms
```

**3. Нестабильная сеть**

Пинг 100 мс, но пакеты теряются пачками (потеря 5% с зависимостью от предыдущего пакета). Проверяет устойчивость сети к микро-разрывам.

```
tc qdisc add dev eth0 root netem delay 100ms 40ms loss 5% 25%
```

**4. Ограниченная пропускная способность**

Искусственное сужение канала до 2 Мбит/с с базовой задержкой.

```
tc qdisc add dev eth0 root netem delay 70ms rate 2mbit
```

**5. Экстремальный стресс-тест**

Потеря 10% пакетов, дублирование, повреждение байтов и нарушение порядка доставки пакетов. Проверяет надежность криптографии и механизмы восстановления.

```
tc qdisc add dev eth0 root netem delay 150ms 50ms loss 5% corrupt 1% duplicate 2% reorder 5%
```


Команда для тестирования через TCP

```
iperf3 -c 10.67.1.1 -t 30
```

Команда для тестирования через UDP

```
iperf3 -c 10.67.1.1 -t 30 -u -b 100M
```

100M - 100мбит/сек

1G - 1гбит/сек
